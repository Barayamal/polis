# Fresh WordPress / MariaDB maintenance candidate

This is a **fresh-only, closed installation candidate**, not a public installer,
an upgrade path, a repair tool, or approval to provision a server. It initializes
the dedicated MariaDB schema and immutable WordPress role used by Build C. It
does not initialize PostgreSQL/Pol.is, the participant service, or a full recovery
bundle, and it cannot activate participation or send invitations.

The normal `Dockerfile.wordpress`, start script and HTTP image remain unchanged.
The two maintenance PHP files must be supplied separately to a short-lived
container made from the exact reviewed normal WordPress image, with networking
disabled, no published ports, a read-only root filesystem, and only the named
disposable material/socket volumes. Do not leave the maintenance material mounted
on a released service. The native synthetic harness mounts it to its QA container
only; that is not a released deployment configuration.

## Inputs and separate authority

Use the existing runtime material at `/run/fncp/wordpress` with its established
UID 33, directory `0700`, single-link files `0400` or `0600`, exact source-owned
paths, key separation, bridge contract and TLS validation. Supply a separate
`/run/fncp/wordpress-initialize/owner.json`, directory UID 33 / `0700`, file UID 33
/ `0400` or `0600`. Its exact keys are:

| Key | Requirement |
| --- | --- |
| `profile` | `FNCP_WORDPRESS_INITIALIZE_V1` |
| `siteTitle` | Non-empty plain UTF-8, at most 120 bytes; no HTML/control characters |
| `operatorLogin` | Lowercase ASCII letter followed by 2–31 lowercase letters, digits or `_` |
| `operatorEmail` | Valid lowercase email address; never sent to by this installer |
| `operatorPassword` | Independently generated canonical base64url encoding of 32 random bytes |

All three JSON files (`config.json`, `plugin-config.json`, `owner.json`) require
sorted-key canonical JSON plus one trailing newline. The existing material
stager uses this format. All database, salt, bridge and operator secrets must be
distinct. Do not put credentials in command arguments, environment variables,
logs, source control or published receipts. No credentials are generated by the
initializer or printed in its output. Actual owner credentials and a live
hostname require the owner's deployment approval; the current harness invents
both locally.

## Ordered maintenance phases

1. Establish an empty, dedicated MariaDB data volume with the reviewed
   `mariadb-install-db`, `--auth-root-authentication-method=socket`,
   `--auth-root-socket-user=root`, and `--skip-test-db`. Start it with
   `--skip-networking`, no host ports, no query logs and a private Unix socket.
   The initializer does not invoke the database daemon or initialize its system
   tables. **Never target a live/recovered instance.**
2. Copy/mount `wordpress-initialize.php` and `wordpress-initialize-lib.php`
   together in the short-lived maintenance container. Run
   `php /run/fncp/maintenance/wordpress-initialize.php database` as UID 0.
   Its root socket account is used only in this maintenance phase. The phase
   requires no non-system schemas and no existing runtime database account. It
   creates only the configured schema/user, with temporary schema DDL plus four
   DML privileges. UID 0 requires narrowly scoped filesystem read/traverse
   authority to read UID 33 `0700` material and reach the socket; the normal role
   never receives that capability.
3. Run the same command with `site` as UID 33, without extra capabilities. The
   configured database must contain **zero tables**. The runtime's own material,
   bridge, CA and leaf checks run before installation. It installs precisely one
   operator, grants that operator `fncp_manage_registrations`, disables signup,
   indexing and default comments/pings, leaves ordinary plugins inactive and
   initializes the bound bridge with zero registrations/events. Only newly
   generated WordPress demonstration posts/comments are removed. Mail is blocked
   before bootstrap; WordPress HTTP is blocked; no provider/event call is made.
4. Run `finalize` as UID 0. It independently reads the site version, exact origins,
   options, sole operator/capability, bound receipt, empty posts/comments and empty bridge. It revokes
   `CREATE`, `ALTER`, `DROP`, `INDEX`, leaving only
   `SELECT`, `INSERT`, `UPDATE`, `DELETE` on this schema, with no grant authority
   or global, other-schema, explicit table/column/routine/proxy or role/default-role
   privileges. Extra host accounts for the same user also reject. Normal runtime never receives the root identity or the
   installation credentials file.
5. Stop/remove the maintenance container and detach its owner/source material.
   Start the unchanged normal WordPress image and run independent private HTTPS,
   staff-login, blocked-installer, empty-state and restart checks. No public
   network or participant opening is implied by a successful check.

The root database phase and schema DDL are not a single atomic transaction. A
failure can leave a partial database. The site phase can likewise fail after
creating tables. **Do not retry, delete, upgrade or repair it automatically.**
Preserve aggregate failure evidence, stop the isolated attempt, and prepare new
explicitly disposable volumes. A second `database` or `site` call is deliberately
rejected; this is not an idempotent live provisioner.

Failure diagnostics include only a fixed stage token, source basename/line and
exception class. They never include exception messages, SQL, tracebacks, secrets
or operator identity. WordPress bootstrap's common global variable names are
isolated from the maintenance configuration snapshot before validation resumes.

The native login probe uses the staff profile page instead of the Dashboard:
[WordPress Quick Draft](https://developer.wordpress.org/reference/functions/wp_dashboard_quick_press/)
can legitimately create an empty auto-draft merely by displaying the Dashboard.
That is not evidence of retained programme content, but it would change a
zero-post rehearsal checkpoint. No dashboard behavior is disabled or hidden in
the runtime; the probe checks a read-only staff page and preserves its empty-state
assertion. Initialization/finalization independently require zero posts/comments
before staff interaction.

## Verification and limits

`node --test deploy/fncp/production-install/wordpress-initialize.test.mjs`
checks exact configuration, secret separation, canonical input, closed snapshots,
identity/capability mismatches, state changes, wrong phases and absence from the
normal runtime Dockerfile. Those host tests do **not** prove a native database
installation. Run `rehearse-wordpress.mjs` against the exact explicit task-local
Docker socket and reviewed image IDs for native evidence. Its own report states
what actually ran; never substitute these unit tests for it.

Readiness still requires integration with the complete zero-port composition,
PostgreSQL/Pol.is installation, fresh full-stack image review/scans, the joined
six-volume recovery rehearsal, and separately approved real identity/TLS and
opening work. WordPress approval remains self-attestation plus operator review;
it is not heritage-document verification.

Fresh installation explicitly selects `/%postname%/`, registers WordPress core
REST rewrite rules and performs a database-only rewrite flush. Both `site` and
`finalize` verify the saved permalink structure and exact `/wp-json/` index/path
rules. This is required by the signed bridge endpoint: WordPress's plain fresh
permalink defaults can serve an HTML theme response at `/wp-json/`, which the
participant bridge correctly rejects. Apache configuration remains immutable;
no `.htaccess` write, registration, approval or invitation is performed by this
routing setup. A native participant rehearsal still verifies the actual HTTP
route and signed response for each final source/image lock.
