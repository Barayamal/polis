# WordPress ↔ synthetic identity binding — independent design review

Design review only: no new bridge code, runtime or proof result is asserted here. Scope is a fresh local synthetic WordPress instance, newly created stores and the strict local access adapter. Existing public services, preserved WordPress/access stores, real identity providers and participant data remain out of scope.

## Minimal integration

1. Keep `wordpress-local/journal.php` as the sole approval/version/outbox authority. Its compare-and-swap commits the decision and immutable event body together; delivery acknowledgements cannot downgrade an earlier ACK. A registration record should hold immutable facts, not a second independently mutable approval state.
2. Add a separately bounded registration/challenge store. In **one atomic CAS or database transaction**, verify and consume the current browser-bound challenge and assertion identity, enforce a unique fixture+round mapping, and create the immutable registration receipt. Never perform consumption and insertion as separate uncoordinated option writes. Concurrent identical submissions must yield at most one registration; an uncertain retry must not substitute a new identity.
3. Under the new strict WordPress mode, replace both the form **and server handler** accepting arbitrary `subject` with a registration-ID-only operation. Resolve fixture/round from the immutable stored row. Retain `manage_options`, POST and action-specific WordPress nonce checks. The old arbitrary-subject handler must not remain usable by direct POST. Existing outbox retries remain exact-body retries.
4. Keep administrator decisions separate from signed identity and self-attestation. Only a registered row with the required recorded facts can reach `journal->change()`. Registration alone must not approve, open a round, create an invitation, or upsert a provider allowlist. Gateway admission still requires current applied WordPress authority, live identity, signed activation and separately open round.

## Security conditions

- **Distinct trust domains:** use distinct keys or derived domain-separated subkeys and exact version/purpose/issuer/audience/round fields for WP challenges, BFF registration assertions and approval-outbox signatures. An approval event, challenge or activation envelope must not validate as another message type. Fixed configured origins only; no payload-selected return URL, key URL or callback destination.
- **Guest browser binding:** independent random HttpOnly/SameSite=Strict cookie and independent CSRF secret, exact Origin/Host, bounded POST body and exact schema. Do not rely on a logged-out WordPress nonce for guest isolation. Rotate the guest capability after successful claim and clear its old challenge. Allow safe cancellation/restart without retaining abandoned authority. HTTP loopback is not production Secure-cookie/TLS assurance.
- **Time and replay:** short lifetime (at most five minutes), bounded future skew, integer timestamps, `issued < expiry`, and expiry no later than the challenge and verified principal lifetime. Check browser/principal/challenge validity again after any asynchronous identity lookup and before signing. One-use assertion IDs and challenge consumption must survive concurrent requests and ambiguous responses; retain necessary tombstones until no still-valid signed assertion can refer to them. Reissuing a challenge invalidates the old one for that guest session.
- **Immutable identity:** derive the fixture only through the strict adapter's live principal. Neither browser fields nor a WP administrator-provided fixture may change the mapping. Enforce both registration-ID immutability and unique fixture+round; reject a new challenge that would overwrite or revive a revoked identity. A new random registration ID must not bypass terminal gateway revocation.
- **Exact self-attestation:** require actual booleans `true` for adult, eligibility self-attestation and consent. PHP form values may be normalized only from an explicit narrow form representation; strings such as `"false"`, arrays and omitted boxes must never become truthy acceptance. Sign and retain a fixed notice version/hash and accepted-at time, so the receipt identifies the wording accepted. These facts are not proof of heritage, age, eligibility or owner launch approval.
- **No confidentiality overclaim:** HMAC authentication does not encrypt an assertion. If its browser-carried payload contains the opaque fixture, the browser can decode it. Either explicitly permit this bounded pseudonymous handoff or use an opaque one-use handle privately resolved by the server; do not say the fixture never reaches the browser. Keep complete challenges/assertions, session IDs, cookies and tokens out of logs, URLs, analytics, screenshots and aggregate reports.
- **Logout versus receipt validity:** offline signature verification cannot discover a BFF logout after assertion issuance. To promise immediate logout invalidation, redeem a one-use capability through a private check against current BFF state and invalidate it on logout/revoke. Otherwise explicitly call the handoff a short-lived registration receipt, not current session authority; it grants no voting access. Principal expiry can still be enforced by the signed receipt's bounded expiry.
- **Revocation/unlink:** do not implement unlink as deleting a registration or changing its fixture. Preserve the mapping and terminal tombstone; issue the next revocation event and distinguish pending delivery from acknowledged provider removal. The existing UI accurately warns that an undelivered WP revocation has not yet removed gateway/provider access. Immediate cross-service withdrawal needs its own acknowledged deny path or a close-round procedure. No deletion/unlink action is implied by this design review.
- **Capacity and failures:** cap guest sessions, pending challenges and registrations independently; never evict a still-valid consumed marker or terminal revocation to admit another registration. Failed registration has no outbox side effect. If registration succeeds but a later approval operation crashes, the row remains pending and the exact journal/outbox can be retried. Preserve failed-run private stores until cleanup is verified.

## Required negative proof matrix

| Boundary | Minimum concrete negative |
| --- | --- |
| Browser binding | Same signed challenge/assertion submitted from a second guest cookie; copied CSRF; duplicate cookie; wrong Origin/Host |
| Replay/atomicity | Two concurrent claims; exact retry after simulated lost reply; reused assertion with a fresh challenge; replaced challenge; crash between intended consume/insert |
| Identity | Forged/copied/expired principal; caller-selected fixture; same fixture under a second registration; different identity attempting to overwrite one row |
| Schema/consent | Missing/false/string/array boolean; extra identity/URL fields; modified notice version; forged signature; wrong message purpose/audience/round |
| Lifecycle | Expired/future assertion, expiry during lookup, cancellation; logout-after-issuance behaviour explicitly tested and labelled |
| WordPress authorization | Subscriber with a nonce; administrator without nonce; arbitrary subject POST to the old handler; unknown/revoked registration ID |
| Outbox | Provider/receiver unavailable during approve and revoke; immutable retry; concurrent admin decisions; stale approval after terminal revoke |
| Access separation | Successful registration without approval, activation or open round still cannot obtain/use voting authority |
| Preservation | Only new local stores/listeners touched; failed cleanup retains diagnostic stores; no participant messages, external issuer traffic or public changes |

The new proof may exercise real WordPress/PHP request handlers, roles, nonce checks and signed local HTTP while still being a **protocol test**, not rendered-browser assurance. The earlier recovery snapshot does not cover new registration/challenge/consent stores or their replay markers. A rollback/restore claim requires a separately updated recovery contract and fresh key/epoch handling.

## Primary references

WordPress states that its nonces are reusable, are not authorization and share the guest user ID by default: [WordPress nonce security](https://developer.wordpress.org/apis/security/nonces/). Administrator handlers still need an explicit capability check: [WordPress capability checks](https://developer.wordpress.org/plugins/security/checking-user-capabilities/). Message-purpose and audience separation follow the same substitution-avoidance principles described in [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.9); the proposed local HMAC envelope is not being represented as JWT compliance.
